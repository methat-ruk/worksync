# Feature Plan: Notifications Foundation

Status: Done

Delivered: 2026-09-02

Plan review: Reviewed, approved, implemented, validated, and post-reviewed

Intended PR: `feat/notifications-foundation`

Milestone: 3 - Comments, Mentions, and Notifications

Impact: Material private user-event feature

## Goal

Persist and display private, workspace-scoped in-app notifications when a task
comment mentions another current workspace member. Delivery, deduplication,
read state, authorization, and client reconciliation must remain deterministic
under transaction retries and concurrent requests.

This foundation provides stored in-app notifications only. Realtime, email,
push, preferences, and task deep-link navigation remain later capabilities.

## Resolved Plan Decisions

- The only source event in this PR is `comment.created` version `1` from the
  delivered comments service.
- One `COMMENT_MENTION` notification is created for each distinct
  `mentionedUserId`; comments without mentions create no notifications.
- Comment, mention, and notification rows are created in the existing
  serializable PostgreSQL transaction. This PR does not add an outbox, worker,
  event bus, or asynchronous delivery.
- Notification items are informative and non-navigable. `TaskDetailSheet` is
  not globally addressable from the app shell; task deep links require a
  separate plan.
- Notifications are deleted when their recipient leaves the workspace or when
  their source comment is deleted. No time-based purge is introduced yet.
- Notification rows store references, not comment bodies or rendered display
  text. Presentation data is resolved at read time after authorization.
- The app shell owns notification list and unread-count state. This PR does not
  add polling or a global state library.

## Acceptance Criteria

- A valid comment mention creates exactly one `COMMENT_MENTION` notification
  for each distinct intended recipient.
- Comment creation, comment mentions, and notification creation commit or roll
  back together, including serializable transaction retries and exhaustion.
- The database prevents more than one notification for
  `(recipientId, type, commentId)`.
- Only the intended authenticated recipient can list or mutate a notification,
  and current workspace/source access is checked before presentation.
- List responses use bounded, deterministic newest-first cursor pagination and
  include an authoritative unread count.
- Mark-one-read and mark-all-read are idempotent and have explicit behavior for
  concurrent list requests and newly committed notifications.
- Removing a workspace member removes that member's notifications for the
  workspace in the same membership-removal transaction.
- The app shell provides an accessible notification button, unread indication,
  panel, loading, empty, error, retry, refresh, and pagination behavior.
- Client reconciliation cannot resurrect accepted read state or overwrite a
  newer unread count with a stale response.
- Contract, real-PostgreSQL, concurrency, security, component, accessibility,
  and live-browser evidence pass.

## Scope

- notification enum, persistence model, relations, indexes, and migration
- typed comment-created event contract and comment-mention mapping
- transaction-aware notification persistence and database deduplication

## Out of Scope

- realtime/WebSocket delivery or polling
- email, mobile push, digests, preferences, or per-event settings
- click-to-task, task deep links, or a globally addressable `TaskDetailSheet`
- notification types other than `COMMENT_MENTION`
- editing, deleting, archiving, or dismissing individual notifications
- time-based retention jobs or read-notification cleanup
- generic event bus, worker, or outbox

## Source Event and Recipient Contract

The source is the existing server-created `CommentCreatedEventV1`:

```ts
type CommentCreatedEventV1 = Readonly<{
  type: "comment.created";
  version: 1;
  workspaceId: string;
  projectId: string;
  taskId: string;
  commentId: string;
  authorId: string;
  mentionedUserIds: readonly string[];
}>;
```

- Move this contract to a dedicated comments event file so notification
  persistence does not depend on the comments service class.
- Accept only the exact type/version pair; unsupported versions fail before
  persistence.
- Recipients are generated by the comments service, never supplied by a
  notification API client.
- The comments service already validates that every mentioned user is a current
  workspace member and rejects self-mentions inside the source transaction.
- Repeated mention occurrences for one user map to one notification.
- The stable logical source identity is the source `commentId`; the stable
  delivery identity is `(recipientId, type, commentId)`.

## Transaction and Module Boundary

- Add a transaction-aware notification persistence service that accepts
  `Prisma.TransactionClient` and `CommentCreatedEventV1`.
- Call it after the comment and `CommentMention` rows are created but before the
  existing comments transaction commits.
- A notification persistence error rolls back the comment, mentions, and all
  notifications for that comment.
- Serializable retry re-executes the whole operation. The database unique
  constraint is the final duplicate-delivery defense.
- Notification persistence depends on Prisma and the event contract; it must
  not call back into the comments service or introduce a circular module
  dependency.
- `NotificationsModule` owns and exports the persistence service and imports
  the existing auth, Prisma, and workspace-authorization modules needed by its
  API. `CommentsModule` imports `NotificationsModule` to invoke persistence.
- `WorkspacesService` performs recipient cleanup directly through its existing
  transaction client; `WorkspacesModule` does not import `NotificationsModule`.
- No event is published after commit in this foundation.

## Persistence Contract

Add the following conceptual Prisma schema:

```prisma
enum NotificationType {
  COMMENT_MENTION
}

model Notification {
  id           String           @id @default(cuid())
  type         NotificationType
  eventVersion Int
  recipientId  String
  workspaceId  String
  commentId    String
  readAt       DateTime?
  createdAt    DateTime         @default(now())

  // User, Workspace, and Comment relations use cascade deletion.

  @@unique([recipientId, type, commentId])
  @@index([recipientId, createdAt, id])
  @@index([recipientId, readAt])
  @@index([workspaceId, recipientId])
}
```

- Add reciprocal relations to `User`, `Workspace`, and `Comment`.
- `recipientId`, `workspaceId`, and `commentId` are server-derived from the
  validated source event.
- Persistence verifies that the referenced comment belongs to the event task,
  project, and workspace; tests protect this denormalized integrity boundary.
- Do not store recipient-facing title/body text, comment excerpts, display
  names, or client-provided JSON payloads.
- The migration is additive, requires no backfill, and must be forward-
  compatible with a rollback to code that does not use the table.

## API Contract

All endpoints require authentication, use the standard API envelope, derive
the recipient from the authenticated user, and never accept a recipient or
workspace ID from the request body.

### List notifications

`GET /api/notifications?limit=<number>&cursor=<opaque>`

- Default `limit` is `20`; maximum is `100`.
- Order is `(createdAt, id) DESC`, newest first.
- The opaque base64url cursor contains validated
  `{ v: 1, createdAt, id }` data and pages strictly after that tuple.
- Only rows whose workspace membership and source resource remain accessible
  to the current recipient are returned.
- Resolve the page, `nextCursor`, and `unreadCount` from one consistent database
  snapshot so a concurrent write cannot make fields within one response
  disagree. Use a Prisma read transaction with PostgreSQL `REPEATABLE READ`
  isolation; keep the serializable retry helper for write transactions.
- Response data:

```ts
type NotificationListData = {
  items: Array<{
    id: string;
    type: "COMMENT_MENTION";
    createdAt: string;
    readAt: string | null;
    actor: { id: string; displayName: string };
    workspace: { id: string; name: string };
    project: { id: string; key: string; name: string };
    task: { id: string; title: string };
  }>;
  nextCursor: string | null;
  unreadCount: number;
};
```

- The public response does not expose `recipientId`, `commentId`, event
  internals, dedupe keys, or comment content.
- `unreadCount` counts currently accessible unread notifications for the
  authenticated user, not only the returned page.

### Mark one notification read

`PATCH /api/notifications/:notificationId/read`

- No request body.
- Run the conditional update, accepted public readback, and unread count in one
  serializable write transaction.
- Set `readAt` only when it is currently `null`; repeated requests succeed with
  the existing value.
- Return the accepted public notification and authoritative `unreadCount`.
- A missing notification and another user's notification both return the same
  `404` contract without revealing existence.

### Mark all notifications read

`PATCH /api/notifications/read-all`

- No request body or client timestamp.
- Run in a serializable transaction. The database transaction timestamp is the
  cutoff and `readAt` value.
- Mark all accessible unread notifications visible in that transaction at or
  before the cutoff.
- A notification committed after that transaction's visibility boundary
  remains unread; serialization conflict follows the project's bounded retry
  behavior.
- Return `{ readAt, updatedCount, unreadCount }` from the accepted transaction.
  The transaction's `unreadCount` is `0`; a later notification may increase it
  on the next list refresh.

## Authorization, Privacy, and Lifecycle

- List and mutation queries include `recipientId = authenticatedUser.id`.
- Read presentation also verifies current membership and that the comment's
  task/project belongs to the recorded workspace.
- Cross-user and inaccessible identifiers use non-revealing `404` responses.
- React renders server-returned strings as text; notification content is never
  interpreted as HTML.
- Logs include event/source IDs, result, and error classification only. They do
  not include comment bodies or rendered notification copy.
- List bounds and indexed queries are mandatory. No process-local rate limiter
  is added; production abuse/load evidence is a revisit trigger.
- During `removeMember`, delete notification rows matching the target
  `(workspaceId, recipientId)` before deleting `WorkspaceMember`, in the same
  serializable transaction.
- Notification relations use cascade deletion for Workspace, User, and source
  Comment records. Account deletion itself remains outside this PR and may
  still be constrained by the repository's other User relations.
- MVP retention is lifecycle-based: retain notifications while both recipient
  membership and source exist. There is no time-based expiration in this PR.
- A production retention period requires a separate background-job/data-policy
  decision before long-term production operation.

## Frontend and Accessibility Contract

- Add a notification button to the authenticated AppShell header.
- The accessible name includes unread state, for example
  `Notifications, 3 unread`; the zero state is `Notifications`.
- Display notifications in a responsive Sheet with heading, close control,
  focus containment, focus return, Escape behavior, and keyboard-operable
  actions.
- Fetch the first page after the authenticated shell mounts. Opening the Sheet
  refreshes the first page unless a request is already in flight.
- Show loading, empty, error with retry, loaded, partial/load-more, refreshing,
  and mutation-pending states distinctly.
- Each item displays current actor, workspace, project, task, timestamp, and
  read state. Items are not links or navigation controls in this PR.
- Primary item copy is `<actor> mentioned you in <task>`, with workspace and
  project context presented separately. Do not display a comment excerpt.
- Each unread item has an explicit `Mark as read` button. The Sheet header has
  `Mark all as read`, disabled when the authoritative unread count is zero or
  while that command is pending.
- Provide a manual refresh action because realtime and polling are out of scope.
- Mark-one and mark-all controls use pessimistic updates: change visible read
  state and count only after an accepted server response.
- Disable duplicate mutation submission while the same target is pending and
  expose recoverable mutation errors without clearing the list.

## Client Reconciliation Contract

The AppShell notification controller is the only owner of pages and
`unreadCount`.

- Give each list request a monotonically increasing request generation; only
  the latest applicable generation may replace first-page state.
- Merge pagination results by notification ID and preserve newest-first tuple
  ordering.
- Treat accepted `readAt` as monotonic: an older list response containing
  `readAt: null` cannot overwrite a locally accepted non-null value.
- A mutation records the request generation visible when it started. List
  responses started before an accepted mutation cannot overwrite that
  mutation's item or unread count.
- After mark-one, apply the returned notification and authoritative count.
- After mark-all, mark currently cached items read using the returned `readAt`,
  apply the returned count, and refresh the first page. Discard list responses
  that began before mark-all was accepted.
- Abort requests on logout or AppShell unmount and ignore responses whose
  authenticated-session identity no longer matches.
- Do not add polling, websocket state, service workers, or a global cache
  library.

## Alternatives Considered

- **Outbox or event bus:** rejected for this foundation because source and
  notification writes use the same PostgreSQL transaction and no asynchronous
  delivery guarantee is in scope.
- **Generic JSON notification payload:** rejected because it duplicates private
  content, complicates authorization after resource changes, and weakens typed
  evolution.
- **Separate unread-count endpoint:** rejected for now because the initial list
  response can establish both the first page and count with one cache owner.
- **Optimistic read state:** rejected because pessimistic accepted responses
  make count and concurrent-arrival behavior easier to prove.
- **Task navigation in this PR:** deferred because the current task-detail UI is
  not globally addressable from AppShell.

## Rollback and Forward Fix

- The migration is additive and has no data backfill. A code rollback keeps the
  notification table and rows intact; do not run a destructive production down
  migration.
- If notification persistence affects comment availability after release,
  redeploy the prior application version while retaining the additive schema,
  then forward-fix the mapping or persistence path.
- UI/API rollback does not corrupt comments or existing notification rows.
- If an authorization defect is found, disable notification API/UI exposure or
  redeploy the prior application version before repairing access logic; do not
  delete evidence-bearing rows as the first response.
- Re-plan before adding cross-service delivery, background cleanup, or a task
  deep-link contract.

## Assumptions and Remaining Decisions

Current verified assumptions:

- Comments and notifications use the same PostgreSQL database and Prisma
  transaction client.
- Mention validation and recipient deduplication occur inside comment creation.
- The current AppShell has no notification entry and no global task-detail
  navigation seam.
- Realtime remains a product requirement but is not acceptance for this
  storage-and-read-state foundation.

No product decision remains open for implementation of this plan. Execution,
schema migration creation, and any later production migration/deployment still
require their applicable authorization.

## Re-plan Conditions

- realtime, polling, email, push, or preferences enter acceptance
- notification items must navigate to a task before a stable task deep-link
  contract exists
- source and notification persistence cross databases or services
- an outbox, worker, or retry queue becomes a current delivery guarantee
- another source event or generic payload framework is added
- time-based retention or legal/data-policy requirements become binding
- query/load evidence requires a materially different unread-count design
